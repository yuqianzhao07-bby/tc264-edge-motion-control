## 一、模块概览

本模块用于在移动机器人路径中识别电路元器件。输入为异常检测触发的坐标和188×120灰度图，输出为识别到的元器件类型、置信度和物理尺寸。

### 整体流水线

```
边界异常检测 → 窗口截取 → OTSU二值化 → 腐蚀分离 → 连通域分析 → 特征提取 → 评分分类 → 多帧确认
```

方向正确，是嵌入式视觉中经典的"检测→分割→识别"范式。

### 窗口大小定义

| 常量 | 值 | 来源 |
|------|-----|------|
| image_w × image_h | 100 × 60 | image.h |
| MT9V03X_1_W × MT9V03X_1_H | 188 × 120 | zf_device_mt9v03x_double.h |
| COMP_WINDOW_W × COMP_WINDOW_H | 120 × 120 | component_recognition.h |

### 支持识别的11类元器件

电阻(Resistor)、电容(Capacitor)、电感(Inductor)、三极管(Transistor)、二极管(Diode)、
开关(Switch)、电池(Battery)、接地(Ground)、电流表(Ammeter)、电源(Power)、运放(OpAmp)

## 二、逐环节分析

### 1. 边界异常检测 (`component_detect_anomaly`, L49-L113)

**方法**：从下往上扫描相邻行边界跳变，取最大 score 的行返回

| 问题 | 严重性 | 说明 |
|------|--------|------|
| 只取"最显著一个"异常行 | ⚠️ 中 | 如果画面中有多个元器件，第二个会被丢掉 |
| 宽度突增与边界跳变混在一起 | ⚠️ 中 | `ANOMALY_BLOB` 和 `ANOMALY_LEFT_JUMP` 可能在同一行同时触发，best_score 只保留一种 |
| 阈值 `ANOMALY_JUMP_THRESHOLD=2` 太敏感 | 🔴 高 | 在60×100缩小图上，2px跳变很可能是噪声。弯道、十字路口也会触发误判 |
| 缺少持续性验证 | ⚠️ 中 | 真正的元器件会连续多行异常，单行跳变可能是噪点 |

**建议**：
- 要求连续3行以上异常才算有效
- 阈值提高到4-5px
- 支持返回多个异常区域（而非仅一个）

---

### 2. 窗口截取 (`extract_window`, L118-L141)

**方法**：以异常点为中心，从188×120灰度图截取120×120窗口

| 问题 | 严重性 | 说明 |
|------|--------|------|
| 窗口120×120 ≥ 图高120 | 🔴 高 | `COMP_WINDOW_H=120`，原始图只有120行高。当cy不为60时，y_start只能是0，窗口几乎占满整幅图，失去局部性 |
| 内存开销大 | ⚠️ 中 | `win_binary` + `win_original` + `win_labels` ≈ 120×120×3 ≈ 43KB，对TC264普通内存压力较大 |

**核心矛盾**：窗口越大越能包住元器件，但120×120已经等于整幅图高度。

**建议**：缩小窗口到70×70或80×80，配合更精准的异常定位和搜索策略（如沿赛道线方向偏移窗口找最大面积连通域）。

---

### 3. 局部OTSU二值化 (`local_otsu`, L146-L194)

**方法**：标准OTSU算法，用 int64 避免溢出

**评价**：✅ 实现正确且健壮。

- int64 方差计算正确
- 局部窗口OTSU比全局阈值更适应光照变化

**局限**：OTSU假设双峰分布。如果窗口内元器件和赛道线灰度接近（比如深色元器件在深色背景上），阈值将无法分离两者。不过在实际亮色赛道上不太常见。

---

### 4. 形态学腐蚀 (`morph_erode_3x3`, L206-L228)

**方法**：3×3腐蚀，1轮迭代。利用"赛道线细长条 vs 元器件块状"的尺寸差异来分离两者。

**核心思路正确**，但存在以下问题：

| 问题 | 严重性 | 说明 |
|------|--------|------|
| 1轮3×3腐蚀可能不够 | ⚠️ 中 | 赛道线8px宽时，1轮3×3只能削掉2px边沿，赛道线仍在6px，仍然连通 |
| 腐蚀不够时回退到原图 | ⚠️ 中 | L981回退意味着赛道线和元器件仍连在一起，连通域分析会把两者合并为一个大区域 |
| 小元器件也被损伤 | ⚠️ 中 | 二极管三角等小形状被腐蚀后变形，影响后续特征提取 |

**建议**：
1. 改用**开运算**（先腐蚀2轮去掉细线，再膨胀1轮恢复元器件形状）：
```c
morph_erode_3x3(win_binary, 2);   // 腐蚀去细线
morph_dilate_3x3(win_binary, 1);  // 膨胀恢复元器件
```
2. 增加膨胀函数（`morph_dilate_3x3`），3×3膨胀：只要有任意邻居为白即设为白

### 5. 连通域分析 (`connected_component_analysis`, L263-L567)

**方法**：4邻域 Union-Find（并查集），路径压缩+按秩合并

**评价**：✅ 算法选择优秀。Union-Find 近线性复杂度 O(n·α(n))，远优于暴力合并。路径压缩和按秩合并都正确实现。

| 问题 | 严重性 | 说明 |
|------|--------|------|
| 标签上限256 | ⚠️ 中 | 120×120窗口噪点多时可能超过256个连通域，溢出后标签混乱 |
| **只取最大面积连通域** | 🔴 高 | 如果元器件不是最大连通域（比如赛道线残块更大，或多元器件共存），会漏掉真正的元器件 |
| `uf_parent[256]` / `uf_rank[256]` 全局static | ⚠️ 低 | 不可重入，但单线程使用无问题 |

**最大隐患**：只取最大连通域→假设元器件面积最大。实际赛道线残块可能面积更大，或多元器件时只能识别一个。

**建议**：
- 改为取**面积前K个**连通域，分别提取特征后综合判断
- 或加最小包围框位置过滤：如果最大连通域跨越窗口中心而元器件应该偏向一侧，则不选

### 6. 特征提取 (L379-L567)

提取了7个特征值用于后续分类：

| 特征 | 可靠性 | 说明 |
|------|--------|------|
| `aspect_ratio` | ✅ T2 | 宽高比，简单可靠 |
| `fill_density` | ✅ T2 | 填充密度 (白像素/包围框面积) |
| `col_segments` / `row_segments` | ✅ T1 | 列/行分段数，不受赛道线影响 |
| `col_profile` / `row_profile` | ✅ 可用 | 投影直方图，好特征 |
| `top_bottom_ratio` | ⚠️ T4 | **存在实现bug** — 见下方 |
| `symmetry_score` | ⚠️ T3 | 只分左右半总像素计数，无列级对应 |

#### 顶底比 (top_bottom_ratio) BUG 详解 (L480-L541)

当前代码：
```c
// 上半部: 找最右白像素列号
for (i = 0; i < top_half; i++)
    for (cx = 0; cx < bbox_w; cx++)
        if (bin[...][...] == 255)
            if (top_width == 0 || cx > top_width) top_width = cx;

// 再找最左白像素列号 top_start
// top_width = top_width - top_start 得到"最宽一行的宽度"
```

**问题**：
1. 只反映"最宽一行"的极值宽度，不是上半部平均宽度
2. 如果元器件内部有空洞或孤立噪声点，`top_width` 会被拉到很远
3. `top_start` 的查找循环写法低效

**建议修复**：用 row_profile 直接取上半部平均宽度：
```c
int16 top_sum_w = 0, top_cnt = 0;
int16 i;
for (i = 0; i < top_half; i++) {
    if (feat->row_profile[i] > 0) {
        top_sum_w += feat->row_profile[i];   // row_profile[i] 就是第i行的白像素宽度
        top_cnt++;
    }
}
float top_avg_w = (top_cnt > 0) ? (float)top_sum_w / top_cnt : 1;

// 下半部同理
// tb_ratio = top_avg_w / bot_avg_w
```

#### 对称性

只统计左右半区像素总数差异（L544-L566），没有做列级对应匹配：
- 一个左偏的矩形和一个右偏的矩形可能得到相同的对称分
- 建议：加入列投影的"镜像对应"匹配度

### 7. 评分制分类器 (`classify_component`, L583-L891) — 核心

**方法**：每种元器件一组 GS（Gaussian-like Soft）评分函数，加权求和，取最高分。

**整体评价**：手工设计11类的规则分类器。框架方向没问题，但有若干根本性缺陷。

#### 问题一：特征空间重叠严重（分辨率 vs 分类粒度）

在188×120分辨率下做11类区分，各类特征分布高度重叠：

```
电阻:   ar≈1.5,  density≈0.35,  sym高
电源:   ar≈1.15, density≈0.55,  sym高
电流表: ar≈1.1,  density≈0.28,  sym高
```

- 电阻和电源的 `ar` 差异仅 1.5 vs 1.15，赛道线干扰下测量波动可能覆盖这个差距
- 电容和开关的 `rows` 差异仅 3 vs 2，一行之差
- 电感和电池都表现为"多行分段+低密度"

#### 问题二：GS函数参数全部靠猜测

```c
s += GS(i_ar,   150, 55, T2_W+5);  // ar≈1.5, width=55, weight=25
s += GS(i_den,   35, 28, T2_W+3);  // fill≈0.35, width=28, weight=23
```

所有 `target`、`width`、`weight` 都是猜测值：
- 真实元器件的 ar 可能根本不是1.5
- density 可能根本不是0.35
- 权重分配无理论/实测依据

#### 问题三：混淆抵抗不够（低置信度问题）

- 最佳分 vs 第二分差距<8时，置信度打4折
- 11类中很多类型本就相近（电阻vs电源、电容vs开关、电感vs电池）
- 实际运行中大量结果将落在低置信区间，影响下游决策

#### 问题四：GS_DIFF宏有符号溢出风险

```c
#define GS_DIFF(a, b)  (((a) > (b)) ? ((a) - (b)) : ((b) - (a)))
#define GS(val, target, width, weight)  \
    ((int16)(((width) > GS_DIFF(val, target)) ? \
        ((int32)(weight) * (int32)((width) - GS_DIFF(val, target)) / (int32)(width)) : 0))
```

当 `width - GS_DIFF(val,target)` 或 `weight * (width - diff)` 超过int32范围时（虽然概率低），结果是未定义的。

#### 问题五：特征可靠性分层（T1-T4）缺少实验验证

```
T1 (最可靠): area, rows, cols   权重系数 25
T2 (较可靠): ar, density         权重系数 20
T3 (一般):   symmetry            权重系数 12
T4 (不可靠): tb_ratio, row_peak  权重系数 8
```

这个分层是合理假设，但未经实测验证。实际赛道上的元器件受光照、视角、赛道线干扰等因素影响，特征可靠性与假设可能偏差很大。

### 8. 多帧确认 (`component_confirm_result`, L1090-L1138)

**方法**：环形缓冲记录最近帧，连续 `CONFIRM_FRAMES` 帧同类型才输出

| 问题 | 严重性 | 说明 |
|------|--------|------|
| `CONFIRM_FRAMES=2` 太少 | ⚠️ 中 | 只能过滤偶发噪声，分类器不稳定时（如在电阻和电源间来回跳），2帧确认无法稳定 |
| 不兼容"少数服从多数" | ⚠️ 低 | 要求所有帧完全一致，如果3帧中有2帧同类型+1帧误判→不输出 |

**建议**：
- 至少3帧确认，采用 2/3 多数规则
- 加入位置一致性检查：同一元器件的 x,y 位置在多帧间漂移不应超过阈值

## 四、改进建议

### 优先级1：减少分类类别（建议先做）

将11类合并为**4个粗类**，先保证粗类准确率：

| 粗类 | 包含原类别 | 签名特征 |
|------|-----------|----------|
| **矩形块** | 电阻、电源 | ar>1.2 + 高sym |
| **多段横线** | 电容、电池、开关、电感 | rows≥2 + 低density |
| **三角/不对称** | 二极管、接地、运放 | tb_ratio偏离1.0 |
| **十字/圆形** | 三极管、电流表 | ar≈1 + 中心投影高 |

### 优先级2：实测校准特征参数

用WiFi图传把窗口截取的二值图发到PC端，人工标注元器件类型，统计每类特征的真实分布（均值和方差），再设定GS的target和width。

### 优先级3：修复顶底比计算

上面已给出具体修复代码。

### 优先级4：改用开运算分离赛道线

```c
morph_erode_3x3(win_binary, 2);   // 腐蚀2轮去细线
morph_dilate_3x3(win_binary, 1);  // 膨胀1轮恢复元器件形状
```

### 优先级5：完善异常检测

- 阈值提高到4-5px
- 要求连续3行以上异常
- 支持多异常区域返回

### 优先级6：改为多连通域Top-K

取面积前K个连通域分别评估，综合判断。

## 六、编译错误修复记录 (2026-06-02)

### 错误类型 1: E244 invalid operand types for + operator / E245 invalid type for left operand of subscript / E272 undeclared identifier "scores"

**原因**：TASKING 编译器的 C 标准模式不允许在 `{ }` 块作用域中声明新变量 `int16 scores[12] = {0}`，也不允许在块中间使用 `int16 i;` 这样的混合声明。代码中的 `scores` 数组被块级作用域 {} 包裹，编译器处理异常。

**修复**：将 `{...}` 代码块展开为平铺代码，或将 `scores` 数组声明提升到函数顶部（在所有块作用域之前）。

### 错误类型 2: unresolved external (__CSA0, __USTACK0, __ISTACK0, __INTTAB_CPU0, ...)

**原因**：TASKING 链接器找不到系统 LSL 文件 `tc1v1_6_x.lsl`。项目自定义的 `Lcf_Tasking_Tricore_Tc.lsl` 第73行 `#include "tc1v1_6_x.lsl"` 需要从 TASKING 安装目录的系统 LSL 路径解析。

**修复**：
1. 在 [Debug/makefile](Debug/makefile):102 中添加 `-d"../Lcf_Tasking_Tricore_Tc.lsl"` 已应用
2. 仍需设置 PRODDIR 环境变量指向 TASKING 安装目录，或在链接器命令中加 `-L` 指定系统 LSL 搜索路径
3. 建议在 AURIX Development Studio 中编译，让 IDE 自动设置环境
