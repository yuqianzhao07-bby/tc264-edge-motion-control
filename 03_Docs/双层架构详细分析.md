### L1：硬件驱动层 — 直接操作寄存器

| 组件 | 文件 | 职责 |
|------|------|------|
| **infineon_libraries/iLLD** | 英飞凌官方底层库 | 芯片外设寄存器封装（GPT12、STM、ASCLIN、QSPI等） |
| **zf_driver/gpio** | `zf_driver_gpio.c` | GPIO 初始化、电平读写 |
| **zf_driver/pwm** | `zf_driver_pwm.c` | ATOM 模块 PWM 输出（电机控制 10kHz） |
| **zf_driver/spi** | `zf_driver_spi.c` / `zf_driver_soft_spi.c` | 硬件/软件 SPI（摄像头 + WiFi） |
| **zf_driver/uart** | `zf_driver_uart.c` | 串口调试输出 |
| **zf_driver/dma** | `zf_driver_dma.c` | DMA 采集摄像头图像（188x120 灰度） |
| **zf_driver/pit** | `zf_driver_pit.c` | 定时器中断（编码器采样、控制周期） |
| **zf_driver/adc** | `zf_driver_adc.c` | ADC 采集（电池电压检测） |
| **zf_driver/encoder** | `zf_driver_encoder.c` | GPT12 编码器方向计数模式 |
| **zf_driver/timer** | `zf_driver_timer.c` | 通用定时器 |
| **zf_common/** | 14个文件 | 时钟配置、FIFO队列、中断管理、调试输出 |

**关键约束：**

| 约束项 | 说明 |
|--------|------|
| 编译器 | TASKING（非 GCC），不能使用 `__attribute__` 等 GCC 语法 |
| 内存管理 | `#pragma section all "cpu0_dsram"` 指定段，无 malloc/free |
| 浮点运算 | 无 FPU 硬件加速，浮点运算靠软件模拟 |
| RAM 限制 | 256KB，大数组必须用 static/全局 |
| 栈空间 | 极小，局部大数组会栈溢出 |

### L2：外设抽象层 — 设备驱动封装

将 L1 的裸驱动封装为功能设备：

| 设备驱动 | 关键函数 | 数据流向 |
|----------|---------|---------|
| **mt9v03x** | `mt9v03x_init()`, DMA 中断回调 | 原始灰度图 `mt9v03x_image[120][188]` |
| **tft180** | `tft180_draw_image()` | 显示赛道图像到 LCD |
| **wifi_spi** | `wifi_spi_connect()` | TCP 发送图像到上位机 |
| **imu660ra** | `imu660ra_get_gyro()` | 三轴角速度 |
| **encoder** | `encoder_get_count()` | 轮子脉冲计数 → 距离/速度 |

**关键设计：**
- 摄像头图像是 188×120 灰度原始数据，经过 `compressimage()` 裁切为 60×100 二值化图像
- 编码器采样周期 10ms，通过 PIT 中断触发
- WiFi 图传支持「原始灰度图」和「二值化图像」两种模式切换

### L3：应用算法层 — 核心业务逻辑

这是项目最有价值的层，包含全部竞赛算法。

#### 3.1 图像处理流水线 (`image.c`)

```
原始灰度图(188×120) → compressimage() 裁切
                     → otsuThreshold() 大津法自适应二值化
                     → turn_to_bin() 转黑白
                     → median_filter() 3×3中值滤波去噪
                     → image_filter() 形态学腐蚀/膨胀
                     → bin_image[60][100] 最终二值图
```

#### 3.2 赛道巡线算法 (`track_way.c` — 45KB，最大文件)

```
核心管线:
bin_image → track_find_line() 边界扫描：
  ├─ 从底部向上 45 行扫描
  ├─ 左/右边界逐行追踪
  ├─ 元素检测：
  │   ├─ ELEMENT_RIGHT_ANGLE  直角弯（边缘跳变检测）
  │   ├─ ELEMENT_T_JUNCTION   T形路口（右手定则入口）
  │   ├─ ELEMENT_CROSS        十字路口（顶部横向赛道检测）
  │   ├─ ELEMENT_OBTUSE       钝角弯
  │   └─ ELEMENT_BREAK        断路
  ├─ 补线逻辑（十字/T形补虚拟中线）
  └─ 弯道回正 (ALIGN_CURVE_EXIT → ALIGN_FORCE)
         │
         ▼
track_get_error() → track_error (横向偏差)
                 → track_angle  (航线角度)
                 → track_element_type (当前元素)
```

#### 3.3 路口导航 (`track_way.c` — DFS 右手法则)

```
右手法则 DFS 遍历所有支路:
  遇到路口 → junction_register() 注册距离指纹
          → junction_decide_direction() 右>直>左>回溯
          → junction_execute_turn() 执行转弯
          → junction_match_backtrack() 距离指纹匹配回溯

状态机: IDLE → APPROACH → REGISTER → DECIDE → TURN → BACKTRACK → COMPLETE
```

#### 3.4 元器件识别 (`component_recognition.c`)

```
边界异常检测 → 窗口截取 → 分类器评分 → 多帧确认 (3帧)
  ├─ COMPONENT_NONE       无元器件
  ├─ COMPONENT_NORMAL     普通元件(电阻/电容/电感/二极管等) → 直接压过
  └─ COMPONENT_TRANSISTOR 三极管 → 十字/Y形特征，需特殊处理
```

#### 3.5 PID 控制器 (`pid_controller.c`)

| PID 实例 | 模式 | 用途 | 参数组 |
|----------|------|------|--------|
| `steering_pid` | 位置式 PD | 横向偏差 → 转向输出 | 直道 Kp=5 Kd=11 / 弯道 Kp=10 Kd=13 / 直角弯 Kp=12 Kd=14 |
| `angle_pid` | 位置式 PD | 航线角度 → 航向修正 | 与位置环并行，三套参数同步切换 |
| `speed_pid` | 增量式 PI | 速度偏差 → 油门修正 | Kp=30 Ki=2 Kd=6，积分抗饱和 ±8000 |

### L4：系统控制层 — 主循环与任务调度

`cpu0_main.c` 是系统的"大脑"，主循环每帧执行完整管线：

```
主循环 (CPU0) - 每帧执行顺序:

  while(TRUE):
    ① 编码器更新             encoder_update() + junction_update_distance()
    ② 等待图像采集完成        mt9v03x_tft180_check_finish()
    ③ 图像压缩+二值化         compressimage() → turn_to_bin()
    ④ 滤波                   median_filter() → image_filter()
    ⑤ 巡线+元素检测          track_find_line() → track_get_error()
    ⑥ 路口遍历状态机         junction_detect_approach() → register → decide → turn
    ⑦ 元器件识别             component_recognize() + 多帧确认
    ⑧ PID 参数切换           adjust_steering_pid() (直道/弯道/直角弯三套)
    ⑨ 双层转向 PID           steer_pid + angle_pid → 合并输出
    ⑩ 速度闭环               speed_pid → 油门修正
    ⑪ 电机输出               my_motor_set_speed(left, right)
    ⑫ 图传+显示              wifi_image_transfer_send()
```

**中断系统 (isr.c)：**

| 中断源 | 触发方式 | 处理内容 |
|--------|---------|---------|
| DMA 中断 | 摄像头采集完成 | 通知主循环有新图像 |
| PIT 定时中断 | 每 10ms | 编码器脉冲采样 |
| 串口中断 | 异步收发 | 调试数据收发 |

## 第三部分：AI 协作四层 Engineering（详细分析）

### L1：Prompt Engineering — 怎么问（精确提问）

> **问法决定输出质量。模糊提问 → 模糊输出；精确提问 → 精确输出。**

五大精确提问技巧：

| 技巧 | 说明 | 本项目示例 |
|------|------|-----------|
| **指定输入格式** | 告诉 AI 你给的是什么 | "输入：`cpu0_main.c` 第 410-550 行" |
| **指定输出格式** | 告诉 AI 你要什么格式 | "输出：C 代码块 + 变更清单表格" |
| **给出反面示例** | 告诉 AI 不要做什么 | "不要用 `// ...` 省略代码" |
| **设定角色** | 让 AI 进入专业模式 | "你是嵌入式工程师，熟悉 TC264 + TASKING" |
| **量化要求** | 用数字代替模糊描述 | "响应时间 < 5ms，内存占用 < 10KB" |

**与本项目代码工程的关系：** 每当需要修改 L3/L4 层代码时，用 L1 精确描述修改目标。

---

### L2：Context Engineering — 给什么（上下文组织）

> **模型不是能力不行，是缺信息。系统化喂信息 > 反复重问。**

本项目必须提供的 6 类 Context：

| Context 类别 | 内容 | 对应代码层 |
|-------------|------|-----------|
| **项目元信息** | 库版本 V3.4.5、主控 TC264、摄像头 MT9V03x | L2 外设抽象层 |
| **硬件约束** | RAM=256KB、无 FPU、无 malloc | L1 硬件驱动层 |
| **编译器约束** | TASKING（非 GCC）、`#pragma section` | L1 硬件驱动层 |
| **代码现状** | 当前相关文件的最新版本、函数签名 | L3 应用算法层 |
| **历史决策** | 为什么选这个方案、之前试过什么失败了 | L4 系统控制层 |
| **待解决问题** | 当前 BUG/需求的具体表现、期望行为 | 全部层 |

**与本项目代码工程的关系：** 围绕代码工程四层，每层注入对应的约束信息，让 AI 准确理解边界。

---

### L3：Harness Engineering — 怎么驾驭（多轮任务拆解）

> **复杂任务不是一条超级 Prompt 搞定，而是多轮对话串联。**

Harness 五阶段流程：

```
阶段1：【理解与规划】→ AI 输出任务分解+执行计划+风险点 → 用户确认
阶段2：【分步执行】  → 每轮只做一个子任务，确认后进入下一轮
阶段3：【集成验证】  → 完整变更清单+模块间兼容性检查
阶段4：【复盘优化】  → 可改进点+技术债务记录
```

**与本项目代码工程的关系：** 按代码工程四层的依赖关系拆解任务——先从 L1 驱动层改起，再到 L3 算法层，最后到 L4 控制层。

---

### L4：Loop Engineering — 闭环执行（目标+步骤+检查+停止）

> **把模糊的"我希望 AI 做好"，改成清晰的"我明确告诉 AI 怎么判断才算做好"。**

Loop 四模块公式：

```
Loop = 目标(Goal) + 步骤(Steps) + 检查(Check) + 停止(Stop)
```

代码复查专用 Loop（详见 `AI对话要求.md` §10.3）：

```
代码修改完成
    │
    ▼
Gate: 编译检查 (0 error 0 warning) → 不通过直接返回
    │ ✅
    ▼
R1: 逻辑复查 (数据流+状态机+计算逻辑+修改针对性)
    │ ✅
    ▼
R2: 边界复查 (数组越界+溢出+除零+循环边界+栈安全)
    │ ✅
    ▼
R3: 集成复查 (接口兼容+模块兼容+时序+内存)
    │ ✅
    ▼
R4: 功能复查 (烧录验证+功能实测+回归测试+对比数据)
    │ ✅
    ▼
输出复查报告 → 提交代码

铁律: 编译不过不进复查 | 每轮不可跳过 | 失败即回退 | 累计3轮失败→卡点报告
```

## 第四部分：真正的开发顺序

### 4.1 运行时执行顺序 vs 开发阶段顺序

**运行时（每帧都执行，不分先后）：**

```
 ① 图像压缩 + OTSU二值化
 ② 中值滤波 + 形态学滤波
 ③ track_find_line()  →  边界/中线/元素 (产生 track_error)
 ④ track_get_error()  →  偏差值 (PID 的输入)
 ⑤ 元器件识别
 ⑥ PID 参数切换 (直道/弯道/直角弯三套)
 ⑦ 双层转向 PID 计算
 ⑧ 速度闭环 PID
 ⑨ 电机输出
```

**开发阶段（严格按顺序，不可跳步）：**

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  阶段1: 图像管线                                                │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 目标: 摄像头拍到图 → OTSU阈值合适 → 二值图黑白分明          │ │
│  │ 验收: 在 TFT180 / WiFi图传上看二值图，赛道线清晰连续        │ │
│  │ 涉及: L4 cpu0_main + L3 image + L2 mt9v03x                │ │
│  └───────────────────────────────────────────────────────────┘ │
│     │ ✅ 图对了                                                 │
│     ▼                                                           │
│  阶段2: 巡线算法                                                │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 目标: track_find_line() 边界追踪正确                        │ │
│  │       track_get_error() 偏差方向和量级对                     │ │
│  │ 验收: 直道时 track_error≈0，弯道时符号对且量级合理          │ │
│  │ 涉及: L3 track_way                                         │ │
│  └───────────────────────────────────────────────────────────┘ │
│     │ ✅ 线对了 → track_error 信号可靠                          │
│     ▼                                                           │
│  阶段3: PID 调参 ★ 当前阶段 ★                                   │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 目标: 用可靠的 track_error 调出稳定的转向+速度响应           │ │
│  │ 流程:                                                      │ │
│  │   1. 用默认参数 (STEER_KP=5, STEER_KD=11) 先跑             │ │
│  │   2. 观察现象:                                              │ │
│  │     ├─ 左右剧烈摇摆 → 减小 Kp, 增大 Kd                     │ │
│  │     ├─ 转弯太慢出界 → 增大 Kp                              │ │
│  │     ├─ 直道蛇形走位 → 增大 Kd (加阻尼)                     │ │
│  │     └─ 转弯后回不来 → 检查弯道参数 STEER_KP_CURVE          │ │
│  │   3. 每改一次 → 烧录 → 实跑 → 记录                         │ │
│  │   4. 直道/弯道/直角弯三套参数都满意 → 锁定                  │ │
│  │ 验收: 全程不冲出赛道，直道不摇摆，弯道顺滑                  │ │
│  │ 涉及: L3 pid_controller + L3 track_way                     │ │
│  └───────────────────────────────────────────────────────────┘ │
│     │ ✅ 车稳了 → 参数锁定                                      │
│     ▼                                                           │
│  阶段4: 高级功能叠加                                            │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 元器件检测: component_recognition → 识别+直行压过           │ │
│  │ 直角转弯:   track_find_line(直角部分) → 大转向+补线         │ │
│  │ 岔路口导航: junction 状态机 → DFS右手法则遍历所有支路       │ │
│  │ 验收: 各项功能单独测试通过后再联合测试                      │ │
│  │ 涉及: 全部 L3+L4 层                                        │ │
│  └───────────────────────────────────────────────────────────┘ │
│     │ ✅ 功能全了                                               │
│     ▼                                                           │
│  阶段5: 整体联合调试                                            │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 所有功能串联，跑完整赛道                                     │ │
│  │ 验收: 全程不冲出赛道，所有元素正确处理                       │ │
│  └───────────────────────────────────────────────────────────┘ │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 为什么必须按这个顺序

```
                  PID 调参只能在阶段3做

  ┌──────────────────────────────────────────────────┐
  │                                                  │
  │  阶段2: 巡线准                                     │
  │  → track_error 信号可靠 ✅                         │
  │     │                                            │
  │     │ 如果 track_error 是错的:                      │
  │     │   例: 车偏右, 但巡线算出偏左                    │
  │     │   → PID 输出: 继续往右转                       │
  │     │   → 车冲出赛道 ❌                              │
  │     │                                            │
  │     │   这种情况下调 PID 参数毫无意义                 │
  │     │   输入信号本身是错的，调再多 Kp/Kd 都没用        │
  │     │                                            │
  │     ▼                                            │
  │  阶段3: PID 调参                                  │
  │  → PID 只能修正"输入正确但输出不够好"的问题           │
  │  → PID 不能修正"输入本身就错"的问题                  │
  │                                                  │
  └──────────────────────────────────────────────────┘

  类比:
    巡线 = 眼睛（告诉我偏差多少）
    PID  = 大脑（决定怎么修正）
    
    眼睛看不清的话，再聪明的大脑也走不对路。
```

## 第五部分：两套四层的关系映射

```
AI 协作四层 Engineering              代码工程四层架构
━━━━━━━━━━━━━━━━━━━━━━━            ━━━━━━━━━━━━━━━━━━━

L4 Loop   (闭环复查)     ─────→    每次修改代码后复查 L3/L4 层产出
                                  Gate→R1→R2→R3→R4 五轮检查

L3 Harness(分轮拆解)     ─────→    按模块拆解:
                                  轮1: 改 L3 image → 轮2: 改 L3 track_way
                                  → 轮3: 改 pid_controller → 轮4: 集成

L2 Context(上下文注入)    ─────→    注入 L1 硬件约束 (TC264/256KB/无malloc)
                                  注入 L2 外设接口 (mt9v03x/tft180/wifi)
                                  注入 L3 代码现状 (函数签名/全局变量)

L1 Prompt (精确提问)      ─────→    精确描述要修改的 L3/L4 层代码段
                                  "读取 track_way.c 第410-550行,
                                   修改直角弯检测阈值为X..."
```

### 实际使用示例：PID 调参过程

```
需求: 弯道方向盘振荡，需要调小 Kp

【L2 Context】注入上下文:
  "当前 STEER_KP_CURVE=10, STEER_KD_CURVE=13
   硬件: TC264 + VNH5019 + 3S电池
   现象: 弯道时车左右摇摆，频率约2Hz"
    ↓
【L1 Prompt】精确提问:

   STEER_KD_CURVE 从 13 增到 15。

   不要改其他参数。"
    ↓
【L3 Harness】多轮执行:
  轮1: 修改参数值
  轮2: 编译验证
  轮3: 烧录+实跑观察
    ↓
【L4 Loop】闭环检查:
  Gate: 编译 0 error ✅
  R1: 逻辑复查 (参数值在合理范围) ✅
  R2: 边界复查 (不影响参数切换逻辑) ✅
  R3: 集成复查 (与角度环/速度环兼容) ✅
  R4: 功能复查 (烧录实跑，摇摆减轻) ✅
  → 输出复查报告 → 提交
```

## 核心总结

| 维度 | 代码工程四层 | AI 协作四层 Engineering |
|------|-------------|------------------------|
| **解决的问题** | 软件长什么样 | 怎么和 AI 一起做好软件 |
| **分层方向** | 从上到下：控制→算法→抽象→驱动 | 从下到上：问→给→驾驭→闭环 |
| **核心原则** | 低层不依赖高层，每层职责单一 | 越往上越系统化，越往下越原子化 |
| **开发阶段** | 阶段1→2→3→4→5，不可跳步 | 每次修改代码都走完整 Loop |

> **代码四层定义了"软件怎么做"，开发顺序定义了"什么时候做"，AI 四层定义了"怎么确保做好"。三套体系协作，才能稳定产出高质量的嵌入式代码。**
