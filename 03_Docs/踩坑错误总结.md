### E001 — 链接脚本文件无法打开

| 项目 | 内容 |
|------|------|
| **日期** | 2026-06-09 |
| **状态** | ✅ 已解决 |
| **错误信息** | `ltc E821: cannot open "../Lcf_Tasking_Tricore_Tc.lsl"` |

**完整错误输出：**
```
ltc E821: cannot open "../Lcf_Tasking_Tricore_Tc.lsl"
amk E451: make stopped
amk E452: target 'Seekfree_TC264_Opensource_Library.elf' returned exit code 1
```

**根因分析：**
- 链接器从 `Debug/` 目录执行，相对路径 `../Lcf_Tasking_Tricore_Tc.lsl` 以 `Debug/` 为起点
- 文件存在于项目根目录，但链接器可能因缓存/权限/工作目录问题找不到
- 该 LSL 文件是空占位（`// Empty LSL file - architecture and derivative are defined by system tc26xb.lsl`），系统会自动加载 `-Ctc26xb`

**解决方案（按优先级尝试）：**

1. **ADS IDE 中 Clean + Build**（最简单推荐）：
   - `Project` → `Clean...` → 选择项目 → `Clean`
   - `Project` → `Build Project`

2. **命令行 clean 重编**：
   ```bash
   cd Debug/
   make clean
   make all
   ```

3. **改为绝对路径**（前两个都不行时）：
   修改 `Debug/.Seekfree_TC264_Opensource_Library.elf.opt` 第1行：
   ```
   # 原：--lsl-file=../Lcf_Tasking_Tricore_Tc.lsl
   # 改：--lsl-file=<项目绝对路径>/Lcf_Tasking_Tricore_Tc.lsl
   ```

**经验教训：**
- 编译出奇怪错误时，**先 clean 再 build** 解决 80% 的问题
- TASKING 编译链中相对路径以 `Debug/` 为起点，不是项目根目录

### E002 — 架构 TC 重复定义（三重冲突）

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-06 |
| **状态** | ✅ 已解决 |
| **错误信息** | `ltc E821: tc_mc_arch.lsl(15): syntax error: two architectures defined with name TC` |
| **调试耗时** | ~40 分钟，7 轮编译迭代 |
| **标签** | `#链接` `#LSL` `#AURIX-1.10.32` `#排查方法论` |

**完整错误输出：**
```
ltc E821: ["D:\AURIX-Studio-1.10.32\tools\Compilers\Tasking_1.1r8\ctc\include.lsl\tc_mc_arch.lsl" 15/14]
          syntax error: two architectures defined with name TC
ltc F018: Invalid LSL file, aborting...
```

**现象：** 编译阶段（`.c → .o`）全部通过，仅在链接阶段失败。Clean + 重编无效。

---

#### 根因分析（三重架构定义来源）

TASKING 链接器通过**三条路径**各自定义了同一个 `architecture TC`，导致重复：

```
路径 1: IDE 插件注入 --lsl-core=vtc     (AURIX Studio 1.10.32 toolchain superClass 默认值)
         → 加载 tc_mc_arch.lsl → 定义 architecture TC

路径 2: .cproject → Other options → -d"../Lcf_Tasking_Tricore_Tc.lsl"
         → 指定项目 LSL 为 derivative 定义文件
         → LSL 内 #include "tc1v1_6_x.lsl" → 加载 tc_mc_arch.lsl → 定义 architecture TC

路径 3: -Ctc26xb (处理器标志)
         → 加载工具链内置 tc26xb 处理器定义
         → 可能也引用了 tc_mc_arch.lsl → 定义 architecture TC
```

**关键文件涉及：**

| 文件 | 位置 | 角色 |
|------|------|------|
| `tc_mc_arch.lsl` | TASKING 工具链内部 | 多核架构定义，包含 `architecture TC { ... }` |
| `Lcf_Tasking_Tricore_Tc.lsl` | 项目根目录 | 项目 LSL，第 73 行 `#include "tc1v1_6_x.lsl"` |
| `.cproject` | 项目根目录 | IDE 配置，Linker → Other options 含 `-d` 标志 |
| `.elf.opt` | `Debug/` 目录 | 链接器实际参数（IDE 自动生成） |

---

#### 排错过程（7 轮迭代）

| 轮次 | 操作 | 新错误 | 学到什么 |
|------|------|--------|---------|
| 1 | sed 删 `.cproject` 的 `--lsl-core=vtc` | 未生效（中文路径编码问题） | sed 在 Windows 中文路径下不可靠 |
| 2 | Edit 工具删 `.cproject` 的 `--lsl-core=vtc` | **E821 依旧** | 删了 `.cproject` 但 IDE 插件仍在注入 |
| 3 | 删 `Debug/` 重编 | **E821 依旧** | `.elf.opt` 重新生成后仍有 `--lsl-core=vtc` |
| 4 | 注释 LSL 第 73 行 `#include "tc1v1_6_x.lsl"` | **E821: no architectures defined** | 架构缺失 — 说明 include 是唯一来源，证明第 1 轮的删除已生效 |
| 5 | 恢复 LSL include，中文注释 | **E821: unexpected char 0xE2** | LSL 预处理器**不支持 UTF-8**，必须纯 ASCII |
| 6 | 改纯 ASCII 注释 | **E821: two architectures TC** → 依旧! | 还有隐藏来源 |
| 7 | grep elf.opt 发现 `-d` 标志 | 仍有 `-d"../Lcf_Tasking_Tricore_Tc.lsl"` | `-d` 是第三个架构定义来源！ |

**关键洞察：** 排错过程不是线性的——每改一处，错误信息变化（重复→缺失→重复），需要根据**错误信息的变化方向**推断还剩几个冲突源。

---

#### 最终解决方案

只需在 AURIX Studio IDE 中完成以下操作：

**第 1 步：** 项目右键 → **Properties** → **C/C++ Build** → **Settings**

**第 2 步：** 左侧导航到 **TASKING Linker** → **Miscellaneous**

**第 3 步：** 右侧 **Other options** 列表中，选中并删除这一行：
```
-d"../Lcf_Tasking_Tricore_Tc.lsl"
```

**保留**以下三项不动：
```
-lcs_fpu
-lfp_fpu
-lrt
```

**第 4 步：** Apply and Close → Clean + Build

> **为什么只删 `-d` 就够了？**
>
> `--lsl-core=vtc` 你在之前的步骤中已经在 IDE 里删除了。`-Ctc26xb` 是处理器选择标志，不能删（编译器也依赖它）。`-d` 标志的作用是「强制指定 derivative 定义文件」，它与 `--lsl-file=` 同时指向同一个 LSL，导致项目 LSL 被双重加载。删掉 `-d` 后，项目的 section_layout 仍通过 `--lsl-file=` 正常加载，但 derivative 只有 `-Ctc26xb` 一处来源 → 不再冲突。

**备选方案（如果 IDE GUI 操作不生效）：**
直接手动编辑 `Debug/.Seekfree_TC264_Opensource_Library.elf.opt`，删除 `-d` 那一行后保存，再 `make all`。但此文件每次 Clean 后会重新生成，只适合临时应急。

**LSL 文件注释规范（附加修复）：**
`Lcf_Tasking_Tricore_Tc.lsl` 第 73 行恢复为：
```c
#include "tc1v1_6_x.lsl"  // architecture TC1V1.6.X definition
```
⚠️ LSL 文件注释必须使用**纯 ASCII 字符**（英文），不允许中文/Unicode 箭头 `←` 等字符（UTF-8 字节 0xE2 会被 LSL 预处理器拒绝：`unexpected char: 0xE2`）。

#### 避坑经验

| # | 经验 |
|---|------|
| 1 | **错误信息的变化 = 最好的线索**：`重复定义 → 无定义 → 重复` 说明删错地方了，换个角度看 |
| 2 | **IDE 插件注入的标志不在 `.cproject` 里**：AURIX Studio 的 toolchain superClass 会注入默认值，需在 IDE GUI 中排查 |

| 7 | **AURIX Studio 1.10.32 升级后旧项目可能不兼容**：新版 toolchain 的默认 LSL 处理方式与旧版不同 |

### E003 — DSRAM 内存段溢出：大数组放错位置导致链接失败

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **错误信息** | `ltc E112: section "cpu0_dsram" is too large` 或类似的内存段溢出 |
| **标签** | `#内存` `#DSRAM` `#链接` `#pragma section` |

**现象：**
编译阶段全部通过，链接阶段报内存段溢出。原因是 CPU0 的 DSRAM 只有 **72KB**，而 `#pragma section all "cpu0_dsram"` 声明范围内的所有变量都被放入这片内存。

**根因：**
```c
// cpu0_main.c
#pragma section all "cpu0_dsram"
int core0_main(void) {
    // ... 所有在函数内声明的大数组都会进 DSRAM ...
}
#pragma section all restore

// 图传叠加缓冲区 60×100 = 6000 字节，DSRAM 放不下！
uint8 overlay_image[image_h][image_w];  // 必须放在普通内存
```

主函数中使用了多个大数组：
- 边界线缓冲区：`x1_boundary[60]` + `x2_boundary[60]` + `x3_boundary[60]` ≈ 540 bytes
- XY 边界模式：`xy_x_boundary[180]` + `xy_y_boundary[180]` ≈ 360 bytes  
- 图传叠加缓冲区 `overlay_image[60][100]` = **6000 bytes**

如果这些全部放进 DSRAM（72KB），加上 iLLD 库的驱动数据结构，很容易超出 72KB 限制。

**解决步骤：**
1. 确认 `overlay_image` 声明在 `#pragma section all restore` **之后**（不放入 DSRAM）
2. 边界线缓冲区加 `static` 修饰减少栈压力
3. 如果还溢出，将初始化时的大数组改为 `malloc` 动态分配（嵌入式不推荐）或减小尺寸

**关键规则：**
```
#pragma section all "cpu0_dsram"    ← 从这里开始全部进 DSRAM
    └─ 时间关键的数据：PID 结构体、全局标志、编码器数据等
    
#pragma section all restore         ← 从这里恢复默认内存
    └─ 非时间关键的数据：调试缓冲区、图传缓冲区、显示缓冲区
```

> ⚠️ **DSRAM 分配原则**：DSRAM 是 CPU0 的"快内存"，仅 72KB，只放需要高速访问的量（PID 状态、编码器数据、全局标志位）。大数组（图像缓冲、图传缓冲）一律放普通内存。

### E004 — IMU 模块禁用的不当处理导致编译/链接错误

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **错误信息** | 编译报 `imu_driver.h: No such file` 或链接报 `undefined reference to imu_*` |
| **标签** | `#编译` `#IMU` `#条件编译` |

**现象：**
决定从双传感器（IMU + 摄像头）切换到纯摄像头模式时，只注释了 `#include "imu_driver/imu_driver.h"`，但代码中仍引用了 IMU 的函数和数据结构，导致编译失败。

**根因：** 禁用一个模块有三种层次，只做到第一层不够：

| 层次 | 操作 | 不够的原因 |
|------|------|-----------|
| 1. 头文件 | 注释 `#include "imu_driver/imu_driver.h"` | 代码中仍引用了 IMU 类型和函数 |
| 2. 源文件 | 从编译列表中移除 `imu_driver.c` | 代码中仍有 IMU 变量声明 |
| 3. 调用点 | 主循环中仍有 IMU 变量读写 | 每个引用点都可能触发编译错误 |

**解决步骤：**
1. 注释 `#include` 头文件
2. 将引用 IMU 全局变量/结构体的代码替换为常量：
   ```c
   // 原来（编译失败）：
   int32 imu_steer_comp = imu_get_steer_compensation();
   
   // 修复后（硬编码禁用）：
   int32 imu_steer_comp = 0;       // 无转向补偿
   int32 imu_pitch_comp = 0;       // 无坡道补偿
   float imu_roll_factor = 1.0f;   // 无侧倾衰减
   ```
3. 在主循环调试输出中删除 IMU 姿态打印语句

**学到的：禁用模块的正确步骤**
- ✅ 在调用点用常量替代 → 后续恢复时搜索 `= 0` / `= 1.0f` 即可找到恢复点
- ✅ 保留原始 IMU 代码（`.c` / `.h` 文件不删除），随时可以恢复
- ❌ 不要只注释 `#include` 就认为模块已禁用

### E005 — 项目重构后 `#include` 路径变化导致找不到头文件

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **错误信息** | `ctc E208: cannot open "pid_controller.h"` / `ctc E208: cannot open "debug_trace.h"` |
| **标签** | `#编译` `#include` `#项目重构` |

**现象：**
项目从平铺结构（所有 `.c` 都在 `User/` 下）重组为分层结构（`02_Start/code/` + `02_Start/user/`）后，若干 `#include` 路径失效。

**根因：**
```
重构前目录结构：
  User/
    cpu0_main.c
    cpu0_main.h
  code/
    pid_controller.h
    image.h
    
重构后目录结构：
  02_Start/
    user/
      cpu0_main.c       ← 文件移动到了这里
    code/
      pid_controller.h  ← 文件移动到了这里
      debug_trace.h
```

`cpu0_main.c` 中原来的 `#include "pid_controller.h"` 不再有效，因为 TASKING 编译器的 include 搜索路径从 `.c` 文件所在目录开始。

**解决步骤：**
1. 检查 Makefile 或 `.cproject` 中的 `-I` include 路径是否覆盖了新的目录结构
2. 对于不在同一目录的头文件，使用相对路径：
   ```c
   // cpu0_main.c 在 02_Start/user/ 下
   #include "pid_controller.h"       // ❌ 在 user/ 下找不到
   #include "../code/pid_controller.h" // ❌ 不推荐，TASKING 路径处理诡异
   #include "pid_controller.h"       // ✅ 依赖 -I 编译选项添加 code/ 路径
   ```
3. 在 `.cproject` 中确认编译选项包含：
   ```
   -I"${ProjDirPath}/02_Start/code"
   -I"${ProjDirPath}/02_Start/user"
   ```

**关键教训：**
- 项目重构时先写 `.cproject` 的 `-I` 路径，再写代码
- TASKING 编译器的 include 搜索顺序：当前目录 → `-I` 指定目录 → 系统目录
- 避免使用 `../` 相对路径 include，改用 `-I` 编译选项统一管理

### E006 — ADS v1.10.32 升级后 "No AURIX device is configured"

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **错误信息** | `No AURIX device is configured in this project.` |
| **标签** | `#编译` `#ADS升级` `#设备配置` |

**现象：**
旧版 ADS 项目升级到 ADS v1.10.32 (Tasking v1.1r8) 后，`Debug/makefile` 被 ADS 自动生成为仅含一条错误信息的阻断脚本：
```makefile
BLOCKING_ERROR = No AURIX device is configured in this project.

all:
	@echo $(BLOCKING_ERROR)
	@exit
```

**根因：**
新版 ADS 要求项目必须包含 `.settings/com.infineon.aurix.buildsystem.prefs` 文件来声明芯片型号。旧项目没有这个文件，ADS 检测不到芯片配置 → 放弃生成真正的 makefile。

**解决：**
1. 创建 `.settings/com.infineon.aurix.buildsystem.prefs`：
```properties
DEVICE-ID=TC26B
DEVICE-ID-FULL=TC26xD_B-Step
aurixDevice=TC26xD_B-Step
AURIX-LIBRARY-PATH=...
LIBRARIES-ROOT-PATH=...
NEVER-EXCLUDE-FROM-BUILD=...
PROJECT-VERSION=1.0
```
2. 创建 `.settings/org.eclipse.core.resources.prefs`（编码配置）
3. 删除 `Debug/makefile`（ADS 重新生成）

**对比参考：** 同目录下 `03_E3_Motor/` 子工程正常编译，因为它们已有 `.settings/` 目录。

### E007 — `-d` 标志导致 LSL 双重加载 → `processor mpe` 重复定义

| 项目 | 内容 |
|------|------|

### P001 — 3S 电池适配：速度参数继承自 2S 导致起步无力/过冲

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **标签** | `#电池` `#速度标定` `#3S` `#参数迁移` |

**现象：**
从 2S 电池（7.4V）切换到 3S 电池（11.1V）后，直接用原来的占空比值，车要么起步打滑要么根本转不动弯。

**根因：**
2S 和 3S 电池输出电压差 **50%**，同样的 PWM 占空比在 3S 下输出功率大得多。直接继承旧参数会导致：

| 参数 | 2S 旧值 | 3S 初始值（继承） | 问题 |
|------|---------|-------------------|------|
| DUTY_MIN | 500 (5%) | 500 (5%) | 3S 下 5% = 2S 下 7.5%，起步太猛 |
| DUTY_MAX | 1800 (18%) | 1800 (18%) | 3S 下 18% = 2S 下 27%，功率过大 |
| BASE_SPEED | 750 (7.5%) | 750 (7.5%) | 3S 下实际速度远超预期 |
| CURVE_SPEED | 650 (6.5%) | 650 (6.5%) | 弯道降速不够，容易冲出去 |

**解决过程：**

| 迭代 | 调整 | 效果 |
|:----:|------|------|
| 1 | DUTY_MIN 500→800 (8%) | 解决起步打滑，但 3S 下 8% 仍偏猛 |
| 2 | DUTY_MAX 1800→2000 (20%) | 确保差速转向时有足够差速空间 |
| 3 | BASE_SPEED 750→850 | 直道速度适中 |
| 4 | CURVE_SPEED 650→800 | 弯道速度与原 2S 效果接近 |
| 5 | 起步 START_SPEED=1200 (12%) 斜坡降至 850 | 避免起步突变冲击编码器 |

**最终 3S 参数：**
```c
#define DUTY_MIN          800     // 8%  (2S 等效用 ≈5.3%)
#define DUTY_MAX          2000    // 20% (确保差速空间)
#define START_SPEED       1200    // 12% 起步斜坡 (100ms 降至 8.5%)
#define BASE_SPEED        850     // 8.5% 直道
#define CURVE_SPEED       800     // 8.0% 弯道
#define RIGHT_ANGLE_SPEED 800     // 8.0% 直角弯
```

**经验公式：** 如果从 2S 迁移参数到 3S：`3S_参数 ≈ 2S_参数 × 0.67`（快速估算），再根据实际赛道微调。

### P002 — PID 参数从编译宏改为运行时变量的初始化陷阱

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **标签** | `#PID` `#在线调参` `#初始化顺序` |

**现象：**
为了实现逐飞助手在线调参（PC 端拖滑块实时改参数），把 PID 参数从 `#define` 宏改为了 `static int32` 运行时变量。编译通过，但调参时速度环参数改了不生效。

**根因：** 初始化顺序错误。

```c
// ❌ 错误做法：g_speed_kp 在 pid_init 之后才赋值
static int32 g_speed_kp = SPEED_KP;  // 编译器在 main() 之前初始化
static int32 g_speed_ki = SPEED_KI;

int core0_main(void) {
    pid_init(&speed_pid, g_speed_kp, g_speed_ki, SPEED_KD);
    // ^ 此时 g_speed_kp 有值（static 初始化在 main 之前），能过
    // 但 pid_update_params 每次循环又用 g_speed_kp 覆盖，等于每次重置
}
```

```c
// ✅ 正确做法：分开初始化和运行时更新
int core0_main(void) {
    pid_init(&speed_pid, g_speed_kp, g_speed_ki, SPEED_KD);
    // 初始值从宏设置，pid_init 只在 init 时用一次

    while(1) {
        // 主循环中再用运行时变量更新（在线调参能改的）
        pid_update_params(&speed_pid, g_speed_kp, g_speed_ki, SPEED_KD);
        // g_speed_kp 可能被在线调参修改过 → 这里把新值写入 pid 结构体
    }
}
```

**关键规则：**
- `pid_init()` 只调用一次，用初始宏值
- `pid_update_params()` 每个控制周期调用，用运行时变量值
- 速度环的 `pid_update_params` 必须在 `pid_calculate` 之前调用
- 宏定义是"出厂默认值"，运行时变量是"当前实际值"

### P005 — 双层 PID 架构的转向输出合并导致各自限幅失效

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **标签** | `#PID` `#双层架构` `#输出限幅` |

**现象：**
双层转向架构（位置环 `STEER_OUT_MAX=1600` + 角度环 `ANGLE_OUT_MAX=800`）各自限幅正常，但合并后 `total_steer` 可能超过 2400，远超单个电机的差速能力，导致弯道"打死方向"——内侧轮停转，外侧轮满速，车辆急转后剧烈振荡。

**根因：**
```c
// 各自限幅：没问题
steer_output  = pid_calculate(&steering_pid, steer_error);  // max ±1600
angle_output  = pid_calculate(&angle_pid, angle_error);     // max ±800

// 但合并后：1600 + 800 = 2400，远超任何一个单环限幅！
total_steer = steer_output + angle_output;
```

在直角弯场景，位置环已经满偏 ±1600，角度环再加 ±800，`total_steer=±2400`，导致差速公式 `target ± total_steer` 中某侧轮占空比被推到 DUTY_MIN（800）或 DUTY_MAX（2000）。

**解决：**
```c
// 合并后再次做总限幅
int32 total_steer = steer_output + angle_output;
if (total_steer > STEER_OUT_MAX) total_steer = STEER_OUT_MAX;   // 1600
if (total_steer < STEER_OUT_MIN) total_steer = STEER_OUT_MIN;   // -1600
```

**经验：多个控制环串联/并联时必须做总输出限幅**，不能只依赖各环自己的限幅。

### P007 — 编码器采样与主循环图像处理时序冲突

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **标签** | `#编码器` `#时序` `#中断` |

**现象：**
偶发性速度值跳变为 0 或极大值。编码器数据显示抖动，速度环 PI 偶尔输出异常大值。

**根因：**
编码器通过 PIT 定时器中断（10ms）更新，主循环中的图像处理（压缩+二值化+滤波）关闭了全局中断：

```c
// cpu0_main.c 主循环
{
    uint32 int_state = interrupt_global_disable();
    compressimage();     // ← 关中断期间编码器 PIT 无法触发
    interrupt_global_enable(int_state);
}
{
    uint32 int_state = interrupt_global_disable();
    turn_to_bin();       // ← 又一次关中断
    interrupt_global_enable(int_state);
}
// ... 滤波、巡线等也耗时 ...
// 最后才读编码器：
encoder_update();
```

如果关中断的时间超过 10ms，就会丢一个编码器采样周期，导致速度值异常。

**解决：**
1. 把 `encoder_update()` 移到主循环**最开始**（在关中断处理图像之前）：
   ```c
   while(TRUE) {
       encoder_update();  // ← 最优先，确保每帧第一时间读取
       // ... 然后才是图像处理
   }
   ```
2. 优化关中断代码块的时间：
   - 压缩和二值化各自独立关中断 → 合并为一个关中断区间
   - 不要在关中断区间内做 `printf` 等耗时操作

### P008 — 电机起步冲击：直接全速导致编码器过冲或轮子打滑

| 项目 | 内容 |
|------|------|
| **日期** | 2026-07-07 |
| **状态** | ✅ 已解决 |
| **标签** | `#电机` `#起步` `#编码器` `#斜坡` |

**现象：**
电机从静止直接给 `BASE_SPEED` 占空比，车轮在光滑赛道面上打滑/弹跳，编码器第一个采样周期的速度值不准确，导致速度环 PI 初始积分异常。

**根因：**
直流电机+减速箱在静止到运动时需要克服静摩擦力。瞬间给较大占空比会导致：
1. 轮子打滑 → 编码器数据 ≠ 实际位移
2. 电流冲击 → 电池电压瞬间跌落
3. 编码器首周期数据异常 → 速度环 PI 积分初值错误

**解决：** 线性斜坡起步
```c
// 从 START_SPEED(12%) 在 100ms 内线性降到 BASE_SPEED(8.5%)
int32 ramp_steps = 10;
int32 ramp_step_ms = 10;
int32 speed_range = START_SPEED - BASE_SPEED;
for (int32 s = 0; s <= ramp_steps; s++) {
    int32 cur_speed = START_SPEED - (speed_range * s / ramp_steps);
    my_motor_set_speed(cur_speed, cur_speed);
    system_delay_ms(ramp_step_ms);
}
my_motor_set_speed(BASE_SPEED, BASE_SPEED);  // 最终确认
```

**经验：** 所有电机起步都要有斜坡，尤其是重负载+高摩擦系数的工况。`START_SPEED > BASE_SPEED` 的"下降斜坡"有助于克服静摩擦。

### IntelliSense 配置要点（最容易踩坑）

要让 VS Code 正确解析 TC264 项目代码，`settings.json` 中必须配好 include 路径和宏定义，否则满屏红色波浪线。

**关键配置项（`.vscode/settings.json`）：**

```json
{
  "C_Cpp.default.includePath": [
    "${workspaceFolder}/code/**",
    "${workspaceFolder}/user/**",
    "${workspaceFolder}/libraries/**",
    "${workspaceFolder}/libraries/infineon_libraries/**"
  ],
  "C_Cpp.default.defines": [
    "TC264D",
    "__TASKING__",
    "__CORE_TC2__"
  ],
  "C_Cpp.default.compilerPath": "C:/Program Files/Infineon/AURIX Studio/tools/.../cctc.exe",
  "C_Cpp.default.intelliSenseMode": "gcc-arm"

```

**常见问题：**
- ❌ IntelliSense 报 `cannot open source file "Ifx_Types.h"` → include 路径没覆盖到 `libraries/` 目录
- ❌ 芯片寄存器定义全红 → 宏 `TC264D` 没加到 defines 里
- ❌ TASKING 特有语法 `__interrupt` 报错 → 正常，VS Code C/C++ 插件不支持 TASKING 扩展关键字

## 📝 避坑经验汇总

### TASKING 编译器

| 坑 | 现象 | 解法 |
|----|------|------|
| 相对路径以 `Debug/` 为起点 | 找不到项目根目录的文件 | 检查 `.opt` 文件路径，改为绝对路径 |
| 增量编译偶尔出问题 | 改了代码但编译结果没变 | `make clean` 后重编 |
| 警告误报（unused variable） | 明明用了还报警告 | 正常，无需处理 |
| LSL 文件空也不要删 | 删了链接器直接报错 | 保留空占位文件即可 |
| `architecture TC` 重复定义 | `ltc E821: two architectures defined` | 逐一排查：`--lsl-core`(IDE插件) → `-d`(Other options) → LSL 内 `#include` → `-Ctc26xb`(处理器)，逐个消除冗余 |
| LSL 不支持 UTF-8 注释 | `unexpected char: 0xE2` | LSL 文件中只能用英文/ASCII 写注释 |
| `.elf.opt` 是排错必看文件 | 链接参数不入 `.cproject` | `grep` 这个文件看链接器实际收到了什么参数 |
| `#pragma section` 放太多东西进 DSRAM | 链接报 section too large | 只放时间关键数据（PID 状态、标志位），大数组放恢复段之后 |
| 项目重构后 include 路径失效 | 找不到头文件 | 检查 `.cproject` 的 `-I` 编译选项，添加新的源码目录 |
| 禁用模块只注释 `#include` | 链接报 undefined reference | 用常量替代调用点的引用，保留源文件不删除 |

### 嵌入式 C

| 坑 | 说明 |
|----|------|
| `int` → `short` 隐式截断 | 嵌入式中数据范围敏感，能用 `int32` 就别用 `short` |
| 中断函数用 `__interrupt` 修饰 | TASKING 特有语法，VS Code 会标红但编译正常 |
| 指针类型要严格匹配 | 编译器会对不匹配报警告，别习惯性忽略 |
| 大数组在 DSRAM 中分配 | TC264 CPU0 DSRAM 仅 72KB，6000 字节的 overlay_image 放进去就爆了 |
| `interrupt_global_disable()` 时间过长 | 关中断期间 PIT 编码器采样会丢周期，导致速度值跳变 |

### 控制算法

| 坑 | 说明 |
|----|------|
| 双层 PID 各自限幅 ≠ 合并后限幅 | 位置环 max 1600 + 角度环 max 800 = 2400，远超单环上限，必须做 Post-merge clamp |
| 参数从宏改为运行时变量 | 初始化用宏，运行中用变量，`pid_update_params` 必须在 `pid_calculate` 之前 |
| 电池电压变化会影响参数 | 2S → 3S 切换需要重新标定所有速度参数（约 ×0.67） |
| 电机起步无斜坡 | 静止摩擦力大于运动摩擦力，直接给 BASE_SPEED 会打滑，需要 START_SPEED 斜坡过渡 |

### 运行时调试

| 坑 | 说明 |
|----|------|
| 初始化死循环 | WiFi/摄像头初始化失败会 `while(1)`，建议至少让 TFT 显示错误码 |
| 参数表与代码不同步 | 改代码不改文档，几天后自己都忘了当前实际值是什么 |
| 编码器在图像处理前读取 | 图像处理关中断可能导致编码器漏采，encoder_update 要放主循环最前面 |

### 开发工具链

| 坑 | 说明 |
|----|------|
| VS Code IntelliSense ≠ 编译器 | IntelliSense 不报错不代表 TASKING 能过，反之亦然 |
| IntelliSense 需要芯片宏 | 不加 `TC264D` / `__TASKING__` 宏，Infineon 库文件全红 |
| ADS 编辑器体验差 | 推荐 VS Code 写代码 + ADS 编译烧录 |
