## 一、工程构建问题修复

### 问题1：`missing separator` 构建失败

**报错信息**：
```
amk F124: ["makefile" 7/0] missing separator.
```

**原因**：
- ADS 新版本不允许 `-lcs_fpu`、`-lfp_fpu`、`-lrt`、`--lsl-file` 写在命令行模式中
- IDE 将错误提示文本直接写入 `Debug/makefile`，破坏了 Makefile 语法
- 同时 `.cproject` 和 `.project` 被误删

**修复方法**：
1. 恢复 `.cproject` 和 `.project`
2. 修改 `.cproject` -> TASKING Linker 配置：
   - 从 `commandLinePattern` 中移除 `=../Lcf_Tasking_Tricore_Tc.lsl`
   - 将 `-lcs_fpu`、`-lfp_fpu`、`-lrt` 从命令行移至 `Other options`
   - 通过 ADS UI 的 Linker → Linker script 配置 LSL 文件路径

### 问题2：`duplicate action for specs.src`

**报错信息**：
```
amk F126: duplicate action for ".metadata/.plugins/org.eclipse.cdt.make.core/specs.src"
```

**原因**：
- `.metadata/.plugins/org.eclipse.cdt.make.core/` 被 ADS 错误扫描为源码目录
- spec.c 和 spec.cpp 生成了重复的 specs.src 编译规则

**修复方法**：
- 修改 `.cproject` 的 `sourceEntries` 排除列表，加入 `|.metadata`
- 删除 `Debug/.metadata/` 目录

### 问题3：库链接失败 `don't know what to do with cs_fpu`

**修复方法**：
- TASKING 的 `Libraries` 选项不支持裸库名
- 将 `cs_fpu`、`fp_fpu`、`rt` 加回 `Other options`，保留 `-l` 前缀（`-lcs_fpu`、`-lfp_fpu`、`-lrt`）

### 最终结果
✅ `0 errors, 10 warnings`，构建成功

## 三、元器件视觉识别 - 技术方案讨论

### 赛道环境
- 蓝色背景 + 白色线路（高对比度）
- 符号固定方向（不需要旋转不变性）
- 元器件：电阻、电容、电感、三极管、二极管、开关、电池等

### 硬件资源
- 摄像头：MT9V03x 188×120 灰度
- 处理分辨率：裁切后 100×60（巡线用）
- MCU：TC264（无 GPU，适合传统图像处理）

### 识别策略（推荐）
- **策略A**：全局扫描 → 二值化后找连通域 → 特征提取 → 决策树分类
- **策略B**：沿赛道线扫描 → 局部窗口检测 → 滑动窗口分析

### 关键挑战
1. 符号和赛道线是**连在一起**的，不能直接用连通域分离
2. 需要沿着赛道线做**局部特征检测**
3. 100×60 分辨率偏低，符号识别可能需要更高分辨率

### 分类特征参考

| 元器件 | 关键特征 |
|--------|---------|
| 电阻 | 矩形框，宽高比约3:1 |
| 电容 | 两条平行竖线，中间有间隙 |
| 电感 | 螺旋/波浪形曲线 |
| 三极管 | Y 形分支 + 箭头 |
| 二极管 | 三角形 + 竖线 |
| 开关 | 两个端点 + 断开 |
| 电池 | 多条长短交替的平行横线 |

### 算法路线
```
原始图像 → 灰度化 → OTSU二值化 → 形态学滤波
    → 赛道线提取 → 沿赛道线局部窗口扫描
    → 窗口内像素投影分析 → 决策树分类 → 输出元器件类型
```

## 七、TFT180显示溢出修复 + 二值化图传配置

### 问题：`zf_assert(x < tft180_width_max)` 断言失败

**报错位置**：`zf_device_tft180.c:460`（`tft180_show_char` 函数内）

**根因**：
- TFT180默认方向为竖屏 `TFT180_PORTAIT`（宽128px）
- 默认字体为 `TFT180_8X16_FONT`（每字符8px）
- WiFi初始化后显示IP地址字符串（如 `10.221.147.220:8086`=19字符），需要 19×8=152px > 128px，溢出

**修复**（`cpu0_main.c:124-126`）：
```c
// 初始化屏幕 (横屏160px + 6x8字体 = 每行最多26字符)
tft180_set_dir(TFT180_CROSSWISE_180);
tft180_set_font(TFT180_6X8_FONT);
tft180_init();
```

两层防护：
| 防护 | 效果 |
|------|------|
| `TFT180_CROSSWISE_180` | 横屏 160px 宽 |
| `TFT180_6X8_FONT` | 每字符6px，每行26字符 |

#### 3. 决策树重写

11类分类器, 优先级从特征最明确到最模糊:

```
NOISE(面积<6)
  ↓
CAPACITOR(双峰投影检测 → 85% | 列分段+间隙 → 70%)
  ↓
SWITCH(行间隙>h/3 + 扁平 → 75% | 2段+对称 → 65%)
  ↓
RESISTOR(宽高比2.5~4+, 填充均匀, 对称 → 65~85%)
  ↓
OPAMP(顶底比>1.8, 上宽下窄, 不对称 → 60~75%)
  ↓
DIODE(顶底比>1.3, 不对称, 单列 → 55~70%)
  ↓
BATTERY(行分段>=4, 低填充, 对称 → 55~70%)
  ↓
GROUND(行分段>=3, 上宽下窄, 低填充 → 55~70%)
  ↓
INDUCTOR(填充<0.48, 行分段>=3, 对称 → 55~65%)
  ↓
TRANSISTOR(列分段>=3, 上窄下宽tb<0.8, 不对称 → 50~65%)
  ↓
POWER(宽高比≈1, 高填充, 对称 → 50~70%)
  ↓
UNKNOWN(弱特征兜底 → 15~35%)
```

#### 4. 关键改进点

| 改进 | 旧方案 | 新方案 |
|------|--------|--------|
| 电容检测 | 仅列分段+间隙 | **+垂直投影双峰检测** (峰值>h/3) |
| 开关检测 | ❌ 不存在 | **+行投影间隙检测** (零值带>h/3) |
| 二极管/运放 | ❌ 无法区分 | **+顶底宽度比** 区分上宽/上窄三角形 |
| 电池/接地 | ❌ 无法区分 | **+顶底比+行分段** 区分横线递减vs交替 |
| 电阻可靠性 | 仅宽高比 | **+对称性+行分段≤3** 排除多段误判 |
| 三极管可靠性 | 仅列分段+面积 | **+上窄下宽(tb<0.8)+不对称** |

### 修复详情

#### 1. 弯道退出检测 (track_way.c)

**问题**: `first_time` 和 `last_bottom_center` 定义在 `ALIGN_CURVE_IN` 块内部, 无法在状态回到 `ALIGN_NONE` 时重置。多段弯道场景下第二次进入弯道时参考值过时。

**修复**: 将变量提升到 `update_align_state()` 函数作用域, 在 `ALIGN_NONE` 状态转换处添加 `align_first_time = 1` 重置。

#### 2. 边界线数据截断 (cpu0_main.c)

**问题**: `(uint8)(left_border[i] & 0xFF)` 只保留低8位, 坐标超255时静默损坏。

**修复**: 改为范围检查 `0-255` 钳位, 负值→0, 超255→255。

#### 3. 连通域分析性能 (component_recognition.c)

**问题**: 等价类合并使用全扫描替换, 最坏 O(n²)。30×30窗口最多900像素, 复杂形状可能产生大量合并。

**修复**: 实现 Union-Find (并查集), 路径压缩 + 按秩合并, 复杂度降至 O(n·α(n)) ≈ O(n)。新增 `uf_find()` 和 `uf_union()` 辅助函数, 内存开销仅 256×2×2 = 1KB。

#### 4. 电容/开关检测排他 (component_recognition.c)

**问题**: 电容外层条件 `rows>=2 && rows<=4` 与开关 `rows>=2` 重叠, 电容未命中时可能误判为开关。

**修复**: 电容外层条件匹配但内层未命中时, 返回 `COMPONENT_UNKNOWN` 而非落入开关检测。同时收紧电容间隙检测: `gap < bh/2` (排除开关的大间隙), `sym > 0.5` (电容对称, 开关不对称)。

#### 5. PID积分器抗饱和 (pid_controller.c)

**问题**: 增量式PID的 `pid->integral` 无上限, 堵转时累积过大, 恢复后输出跳变。

**修复**: 增量式分支增加 `±8000` 积分限幅, 与位置式一致。

#### 6. OTSU阈值下限 (image.c)

**问题**: 硬编码 `Threshold >= 45`, 极暗环境下OTSU最优值被截断。

**修复**: 改为 `max(MinValue+10, 45)`, 在极暗场景下使用更宽松的下限。

#### 7. 起步加速斜坡 (cpu0_main.c)

**问题**: 从 `START_SPEED=1300` 突变到 `BASE_SPEED=850`, 电机会反向制动冲击。

**修复**: 分10步线性斜坡, 每步10ms, 共100ms平滑过渡。

#### 8. 摄像头失败显示 (cpu0_main.c)

**问题**: 摄像头初始化失败时 `while(1)` 死循环, 但之前已 `tft180_clear()` 清屏, 用户看不到WiFi连接信息。

**修复**: 不再清屏, 保留WiFi信息, 额外显示 "Check MT9V03x" 提示。

| **异常检测不可靠** | 边界跳变检测经常漏检, 导致不触发识别 |
| **位置跳变** | 每帧扫描位置不同, 识别结果不稳定 |
| **扩展困难** | 每加一种元器件, 都要调整窗口位置和偏移量 |
| **内存消耗大** | 70×70窗口 = 9.8KB 缓冲区 |

## 二、新方案: 赛道线宽度分析法

### 核心思路

**不用窗口裁切, 直接分析赛道线每行的宽度变化。**

元器件附着在赛道线上 → 赛道线在该区域**变宽** → 根据变宽区域的**形状**判断是什么元器件。

```
正常赛道线:              有元器件:
宽度                     宽度
┃                        ┃
┃███ (正常宽度)          ┃███ (正常)
┃███                     ┃███████ ← 变宽了! 这就是元器件
┃███                     ┃███████
┃███                     ┃███████
┃███                     ┃███ (正常)
┃███                     ┃███
```

### 宽度曲线

逐行计算赛道线宽度, 画出"宽度曲线":

```
行号    宽度    宽度曲线
 0      12     ████████
 1      12     ████████
 2      12     ████████
 3      20     ████████████████  ← 变宽
 4      22     ██████████████████ ← 最宽
 5      20     ████████████████  ← 变宽
 6      12     ████████
 7      12     ████████
```

### 元器件分类依据

根据宽度曲线的**形状特征**判断类型：

| 元器件 | 宽度曲线形状 | 关键特征 |
|--------|-------------|---------|
| 电阻 | 矩形凸起 | fill_ratio高, 对称, 单段 |
| 电容 | 双峰+间隙 | segments=2, 有gap |
| 电感 | 锯齿波动 | segments多(3+), 低fill |
| 三极管 | 中间突起 | peak在中间, fill中等 |
| 二极管 | 逐渐变宽 | tb<1, peak在底部 |
| 开关 | 大间隙 | max_gap大 |
| 电池 | 多段凸起 | segments多, 低fill |
| 接地 | 递减 | tb>1, peak在顶部 |
| 电源 | 对称凸起 | 高fill, 高symmetry |
| 运放 | 下宽上窄 | tb<1, fill较高 |
| 电流表 | 对称+中心突起 | symmetry高, peak在中间 |

### 优势

| 对比项 | 窗口裁切 (旧) | 宽度分析 (新) |
|--------|-------------|-------------|
| 位置要求 | 必须精确对准 | **不需要**, 沿赛道线自动检测 |
| 漏检率 | 高 (位置偏就漏) | **低** (全行扫描) |
| 稳定性 | 跳变 | **稳定** |
| 扩展性 | 差 (每种要调位置) | **好** (只需记宽度模式) |
| 内存 | 9.8KB窗口 | **0额外内存** (复用赛道线数据) |
| 计算量 | 高 (裁切+二值化+连通域) | **低** (只算宽度差) |

### 14.3 分类器 v12：整数线性评分替代高斯评分

**致命缺陷**：旧版 `G(val, c, w, ms) = ms × (1 − (val−c)²/w²)` 在 `|val−c| > w` 时产生**无下限负分**。

以实际连通域 `sym=0.5, density=0.7` 为例：
- G(sym×100=50, 90, 12, 25) = 25 × (1 − 1600/144) = **−252**
- G(density×100=70, 30, 18, 15) = 15 × (1 − 1600/324) = **−59**

**一个维度偏离就能毁掉总分。所有11种类型得分全是负数。**

**修复**：用整数线性截断评分 GS 宏替代：

```
旧: G(val, c, w, ms)  = ms × (1 − (val−c)²/w²)  ← 高斯, 负分无下限
新: GS(val, c, w, ms) = ms × max(0, 1 − |val−c|/w) ← 线性截断, 最小0分

纯整数实现: ms × (w − |val−c|) / w
```

**关键改进**：
- 绝不产生负分：一个维度不符合只得0分，不影响其他维度
- 纯整数运算：无浮点开销，适合嵌入式
- 每类型基础分 10-20 + 截断输出 `max(0, s)`

**11种元器件评分参数调优**（[component_recognition.c](code/component_recognition.c) 完整重写）：

| 类型 | 核心特征 | 其他特征 | 约束 |

| 电阻 | sym≈80, tb≈95 | den≈35, ar≈150, row_peak≈13 | tb不极端, rows≤4 |
| 电容 | rows≈3, sym≈80 | tb≈100, den≈25, row_peak≈16 | den<50 |
| 电感 | den≈15 (极低) | sym≈80, rows≈5, ar≈140 | den>40扣分, rows<3扣分 |
| 三极管 | row_peak≈22 (峰值突出) | row_var, den≈40, sym≈80 | row_peak<15扣分 |
| 二极管 | `\|tb−1.0\|`≈55 (双向) | den≈55, sym≈70, ar≈130 | `\|tb−1.0\|`<30扣分 |

| 电池 | rows≈5 | den≈30, sym≈70 | rows<3扣分 |

### 14.4 形态学腐蚀：分离赛道线与元器件

**根本问题**：OTSU二值化后，赛道线（细长条，4-8px宽）和元器件（块状，15-40px）连成一片。连通域分析找到一个包含两者的 blob → 特征完全失真 → 分类失败。

**解决方案**：在 OTSU 和连通域分析之间插入 3×3 形态学腐蚀（1轮）：

```
OTSU二值化 → 3×3腐蚀(1轮) → 连通域分析 → 分类
                 ↓ (area<10时回退)
             用原始二值图重做CCA
```

- **3×3腐蚀原理**：仅当9个邻域像素全为 255（白）时保留该像素
- **细赛道线**（<5px宽）：边沿像素被移除，连接断开
- **块状元器件**（>15px）：只缩小一圈，形状保留
- **回退机制**：腐蚀后若 `area<10`，自动用原始二值图重做连通域分析

**新增**：
- `morph_erode_3x3()` — 形态学腐蚀函数
- `win_original[120][120]` — 原始二值图备份缓冲（14.4KB，静态分配）

### 14.5 二极管方向依赖修复

**问题**：二极管在一个方向能识别（tb≈0.5, 上窄下宽），翻转方向后失效（tb≈1.5）。

**修复**：用 `|tb_ratio − 1.0|`（离对称轴的距离）替代固定的 `tb < 0.8`：

int16 tb_dist = (i_tb > 100) ? (i_tb - 100) : (100 - i_tb);
s += GS(tb_dist, 55, 50, 30);  // |tb−1.0|≈0.55 → 不管哪个方向都能得分
```

### 14.10 分类器 v13：特征可靠性分层 + 混淆抵抗 + 差距置信度

#### 问题1: 特征可靠性倒挂

| 特征 | 受赛道线污染 | v12 表现 | v13 改进 |
|------|------------|---------|---------|
| rows, cols | 几乎不受影响 | 权重分散 | **T1层, 基础权重25** |
| ar, density | 轻度影响 | 权重中等 | **T2层, 基础权重20** |
| symmetry | 中度影响 | 权重偏高 | **T3层, 基础权重12** |
| tb_ratio, row_peak, row_var | 严重影响 | **权重最高(30-35)** | **T4层, 仅8** |

#### 问题2: 相似类型缺乏区分度

v13 为每对易混淆类型添加"混淆抵抗"逻辑：

| 易混淆对 | 区分策略 |
|---------|---------|
| 电阻 ↔ 电源 | 电阻密度>55软惩罚; 电源密度<30软惩罚 |
| 接地 ↔ 运放 | 接地密度>55软惩罚(密度低); 运放tb<115软惩罚(tb更高) |
| 电池 ↔ 电感 | 电感密度>35软惩罚; 电池密度<10软惩罚 |
| 二极管 ↔ 接线柱 | tb_dist<25软惩罚(必须不对称) |
| 三极管 ↔ 电容 | i_rpr>18软惩罚(电容无峰值) |

#### 问题3: 硬惩罚悬崖

v12: `i_den > 40 → s -= 15` (密度40→41突变15分)
v13: `s -= GS(i_den, 55, 20, 12)` (平滑过渡, 密度55满分→75零分)

#### 问题4: 置信度只看绝对分

v12: `confidence = best_score` (99分vs98分 = 99%)

```

gap ≥ 15 → conf = 绝对分 × 80%   (较明显)
gap ≥ 8  → conf = 绝对分 × 60%   (略有优势)  
gap < 8  → conf = 绝对分 × 40%   (几乎平手)
```

    track_element_type = ELEMENT_NONE;
    
    // 条件判断链
    if (inner_right && !inner_left && !top) {
        // 右直角弯
    } else if (!inner_right && inner_left && !top) {
        // 左直角弯
    } else if (inner_left && inner_right && top && !horizontal) {
        // 十字路口 → 直穿
    } else if (inner_left && inner_right && top && horizontal) {
        // T字路口 → 右转补线
    } else if ((inner_right || inner_left) && top) {
        // 单侧+顶部 → 正常巡线
    } else if (!inner_left && !inner_right && top) {
        // 正常直道
    } else if (!inner_left && !inner_right && !top) {
        // 全无 → 检查偏移判断弯道
    }
}
```

## 三、右手法则 + 方向记忆

### 3.1 核心思想

```
右手法则: 每个路口优先右转
方向记忆: 记录每个路口哪些方向走过
编码器距离: 识别"我在哪个路口"
```

### 3.2 路口记录数据结构

```c
typedef struct {
    int32 seg_distance;     // 到上个路口的距离（指纹）
    int32 abs_distance;     // 绝对距离（回溯时备用）
    uint8 dirs_available;   // 可走方向 (bit0=直, bit1=左, bit2=右)
    uint8 dirs_tried;       // 已走过方向
    uint8 entry_dir;        // 进入方向
    uint8 backtrack_count;  // 回溯次数
} JunctionRecord;
```

### 3.3 方向编码

| 方向 | 编码 | bit位 | 说明 |
|------|------|-------|------|
| 直行 | 0 | bit0 | 从这个方向驶入 |
| 左转 | 1 | bit1 | 左转 |
| 右转 | 2 | bit2 | 右转 |
| 回溯 | 3 | — | 掉头回上个路口 |

### 3.4 路口类型与可走方向

| 路口类型 | 形状 | 可走方向 | dirs_available |
|----------|------|---------|---------------|
| ⊥形(上T) | 顶部横向，左右有路 | 左+右 | 0b110 |
| ├形(左T) | 左侧有路 | 左+直行 | 0b011 |
| ┤形(右T) | 右侧有路 | 右+直行 | 0b101 |
| 十字 | 四方向都有路 | 左+直+右 | 0b111 |
| 只能左转 | 左侧有路 | 只有左 | 0b010 |
| 只能右转 | 右侧有路 | 只有右 | 0b100 |
| 只能直行 | 只有前方 | 只有直 | 0b001 |

## 四、方向决策算法

### 4.1 决策逻辑

```c
uint8 decide_direction(JunctionRecord *j) {
    // 优先级: 右(2) > 直(0) > 左(1)
    uint8 priority[] = {DIR_RIGHT, DIR_STRAIGHT, DIR_LEFT};
    
    for (int i = 0; i < 3; i++) {
        uint8 dir = priority[i];
        uint8 mask = (1 << dir);
        
        // 条件1: 这个方向可走
        // 条件2: 这个方向没走过
        if ((j->dirs_available & mask) && !(j->dirs_tried & mask)) {
            j->dirs_tried |= mask;  // 标记已走
            return dir;
        }
    }
    
    // 全走过了 → 回溯
    j->backtrack_count++;
    if (j->backtrack_count >= MAX_BACKTRACK) {
        return DIR_STRAIGHT;  // 放弃，直行
    }
    return DIR_BACK;
}
```

### 4.2 注册新路口（修正版）

```c
void register_junction(int32 current_dist) {
    JunctionRecord *j = &junctions[junction_count];
    j->seg_distance = current_dist - last_junction_dist;
    j->abs_distance = current_dist;  // 绝对距离（回溯时备用）
    j->dirs_available = detect_available_directions();
    j->entry_dir = detect_entry_direction();  // 检测进入方向
    j->dirs_tried = (1 << j->entry_dir);     // 标记进入方向已走
    j->backtrack_count = 0;
    junction_count++;
}
```

**关键修正**：
- `dirs_tried` 根据实际进入方向设置，不再硬编码为直行
- `abs_distance` 记录绝对距离，回溯时用于备用匹配

### 4.3 决策示例（修正版）

**例1：⊥形路口（左+右），从底部进入**
```
dirs_available = 0b110 (左+右)
dirs_tried初始 = 0b001 (进入方向=直行，已标记)

第一次: 右(2)可走且未走 → 选右转, dirs_tried=0b101
第二次: 右已走 → 左(1)可走且未走 → 选左转, dirs_tried=0b111
第三次: 全走过 → 回溯
```

**例2：├形路口（左+直行），从底部进入**
```
dirs_available = 0b011 (左+直行)
dirs_tried初始 = 0b001 (进入方向=直行，已标记)

第一次: 右(2)不可走 → 直(0)已走过(进入方向) → 左(1)可走 → 选左转, dirs_tried=0b011
第二次: 全走过 → 回溯
```

**例3：只有右转，从底部进入**
```
dirs_available = 0b100 (只有右)
dirs_tried初始 = 0b001 (进入方向=直行，已标记)

第一次: 右(2)可走且未走 → 选右转, dirs_tried=0b101
第二次: 全走过 → 回溯
```

**例4：十字路口，从底部进入**
```
dirs_available = 0b111 (左+直+右)
dirs_tried初始 = 0b001 (进入方向=直行，已标记)

第一次: 右(2)可走 → 选右转, dirs_tried=0b101
第二次: 直(0)已走过 → 左(1)可走 → 选左转, dirs_tried=0b111
第三次: 全走过 → 回溯
```

**关键点**：进入方向自动标记为已走，所以直行方向不会再被选（除非是从左或右进入）。

## 五、路口识别（编码器距离指纹）

### 5.1 核心思想

每个路口有唯一的"指纹"——它到上个路口的距离。

```
起点 ----800脉冲---- J1 ----500脉冲---- J2
                     ↑                ↑
                  指纹=800          指纹=500
```

### 5.2 识别流程（修正版：两级匹配）

```c
int find_junction(int32 current_dist) {
    int32 seg_dist = current_dist - last_junction_dist;
    
    // 第1级: 段距离匹配（正常行驶时有效）
    for (int i = 0; i < junction_count; i++) {
        if (abs(seg_dist - junctions[i].seg_distance) < TOLERANCE) {
            return i;
        }
    }
    
    // 第2级: 绝对距离匹配（回溯时备用）
    // 回溯时路径可能不同，段距离不可靠，用绝对距离
    for (int i = 0; i < junction_count; i++) {
        if (abs(current_dist - junctions[i].abs_distance) < ABS_TOLERANCE) {
            return i;
        }
    }
    
    return -1;  // 新路口
}
```

**关键修正**：
- 增加第2级绝对距离匹配，解决回溯时距离指纹失效问题
- `ABS_TOLERANCE` 比 `TOLERANCE` 更大（如300脉冲），容差更宽

## 六、转弯执行

### 6.1 转弯状态机

```
IDLE → 检测到路口 → LOCKING(直行100脉冲)
     → 距离到达 → TURNING(差速转弯)
     → 中线回正 → CONFIRM(连续5帧确认)
     → 确认通过 → IDLE(恢复巡线)
```

### 6.2 各阶段电机控制

| 阶段 | 电机控制 | 退出条件 |
|------|---------|---------|
| LOCKING | PID巡线(不覆盖) | 编码器距离 ≥ 100脉冲 |
| TURNING | 差速: 慢轮600/快轮800 | 中线偏移 ≤ 8像素 且 距离 ≥ 200脉冲 |
| CONFIRM | 保持差速 | 连续5帧中线偏移 ≤ 8像素 |

### 遍历过程（修正版）

```
步骤  位置  动作              J1状态           J2状态           说明
──────────────────────────────────────────────────────────────────────
 1    起点  出发              -                -                从起点进入J1

 9    J2    已知,选左转       -                tried=110

## 十、总结

### 核心要素

| 要素 | 作用 | 实现方式 |
|------|------|---------|
| 路口检测 | 发现岔路口 | 摄像头识别T字/十字 |
| 路口识别 | 知道"我在哪个路口" | 编码器距离指纹 |
| 方向记忆 | 知道"哪些路走过" | dirs_tried位掩码 |
| 方向决策 | 知道"该走哪条路" | 右手法则优先级 |
| 转弯执行 | 实际转向 | 差速转弯+中线回正 |
| 死路检测 | 发现支路尽头 | 赛道中断/元器件 |
| 回溯机制 | 返回上个路口 | 掉头+距离匹配 |

### 优势

1. 每条支路只走一次，重复路径最小
2. 不需要全局地图，只需要局部信息
3. 实现简单，位掩码+遍历
4. 适应性强，自动处理各种路口形状

### 局限

1. 假设赛道是树形结构（无环路）
2. 距离指纹在回溯时可能失效（已用绝对距离匹配缓解）
3. 需要准确的路口检测

元素识别的真正目的不是"分类元件"，而是**检测赛道结构变化（T形节点）**。

### 元件检测方法（修正）

**问题**：最初用"赛道宽度异常"检测元件，但元件垂直于赛道时不增加宽度，会漏检。

**修正**：改为检测赛道宽度的**局部凸起**：
- 比较最近10行的宽度
- 如果某几行的宽度比平均宽度大 8-25px → 元件区域
- 最大宽度 ≤ 50px（排除平行支路）

```c
// 计算最近10行宽度
int16 widths[10], max_w = 0, avg_w = 0;
for (wi = image_h-1; wi >= image_h-10; wi--) {
    widths[count++] = right_border[wi] - left_border[wi];
}
avg_w = sum / count;
max_w = max(widths);

// 局部凸起检测
int16 bump = max_w - avg_w;
if (bump >= 8 && bump <= 25 && max_w <= 50) {
    track_element_type = ELEMENT_COMPONENT;  // 检测到元件
}
```

### 决策树（精简版）

```
1. 内区单侧有 + 顶部无 → ELEMENT_RIGHT_ANGLE（直角弯）
2. 顶部有 + 仅单侧内区有 → ELEMENT_T_JUNCTION（T形路口）⭐
3. 两侧内区都有 + 顶部有 → ELEMENT_CROSS（十字）
4. 顶部有 + 内区无 + 局部凸起8-25px → ELEMENT_COMPONENT（元件，直行压过）
5. 顶部有 + 内区无 + 宽度正常 → ELEMENT_NONE（直道）
6. 全无标志 + 中线偏移>20 → ELEMENT_RIGHT_ANGLE（直角弯漏检）
7. 全无标志 + 中线偏移≤20 → ELEMENT_BREAK（断路）
```

## 十五、电机速度参数调优 — Loop Engineering 实践 (2026-07-06)

### 背景

使用 Loop Engineering 方法论（目标→步骤→检查→停止）完成参数调优。

### 一、目标 (Goal)

**做什么：** 将 cpu0_main.c 中所有电机控制参数从 2S 电池适配到 3S 电池
**做到什么程度：**

## 十六、ADS v1.10.32 编译修复 — 三层错误的逐步排查

### 背景

项目从旧版 ADS 迁移到 ADS v1.10.32 (Tasking v1.1r8) 后，编译失败。经过三层逐步排查和修复。

### 错误链

```
E006: "No AURIX device is configured"
  → 创建 .settings/com.infineon.aurix.buildsystem.prefs
  ↓
E002: "architecture TC defined twice"
  → 从 .cproject 删除 --lsl-core=vtc
  ↓
E007: "processor mpe defined more than once"
  → 从 .cproject 删除 -d"../Lcf_Tasking_Tricore_Tc.lsl"
  ↓

```

### 根因分析

对比能正常编译的 `Track_Car_01` 项目，发现 Track_Car_Final 的 `.cproject` 中 Linker → Other options 多了一条 `-d"../Lcf_Tasking_Tricore_Tc.lsl"`：

|---|---|---|
| `--lsl-file=` | ADS 自动生成 | ADS 自动生成 |
| `-d"../Lcf..."` | **无** | **多余！** |

`-d` 等同于 `--lsl-file`，导致项目 LSL 被加载两次 → 其中 `processor mpe` 被定义两次 → 链接失败。
